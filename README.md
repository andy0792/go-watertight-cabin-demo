# go-watertight-cabin-demo

> **Go 实现的网页可视化教学 Demo，演示水密隔舱模式（Bulkhead）+ 信号量并发限流 + 熔断器 CircuitBreaker + 业务降级 Fallback + 网页故障注入。**
>
> 非开发人员仅靠点击按钮、修改网页数字就可以理解分布式故障隔离原理。

## 项目概述

**类比轮船水密隔舱：** 单个舱故障进水，不会造成整艘船沉没；业务模块故障，不会把整个应用拖垮，实现故障隔离。

本 Demo 完整实现分布式高可用保护的**三板斧**：

| 机制 | 一句话区分 | 作用对象 | 核心目的 |
|------|-----------|---------|---------|
| **限流** | 防流量太大，管入口 | 挡突发流量，保护自己不被打垮 | 控制并发/请求量，超出阈值直接拒绝 |
| **熔断** | 防雪崩，管下游 | 下游大量报错就切断调用 | 防止故障链式扩散 |
| **降级** | 防自己扛不住，管自身 | 舍弃非核心逻辑，返回兜底结果 | 保障核心业务可用 |

**三者配合分工：** 限流挡流量，熔断断坏依赖，降级保核心业务。

> 💡 **记忆口诀：** 限流挡流量，熔断断下游，降级保自己。

## 核心概念

| 概念 | 通俗比喻 | 网页 UI 标识 |
|------|---------|-------------|
| **水密隔舱 (Bulkhead)** | 轮船独立隔间，一个隔间故障，其他隔间不受影响 | 3 张独立业务卡片面板 |
| **并发限流（信号量）** | 窗口最多同时接待 N 个人，人多直接告知繁忙 | 参数：最大并发 |
| **熔断器 Closed** | 业务健康，全部请求放行 | 🟢 Closed 正常（允许访问） |
| **熔断器 Open** | 业务故障，拒绝新来请求，阻止故障扩散 | 🔴 Open 熔断阻断（拒绝访问） |
| **熔断器 HalfOpen** | 冷却结束，放少量请求试探业务是否修复 | 🟡 HalfOpen 试探恢复（小流量测试） |
| **降级 Fallback** | 熔断打开，不走真实业务，返回缓存兜底数据 | 指标：降级次数 |
| **故障注入** | 模拟下游故障概率，0-100% 可调 | 每个舱面板：勾选框 + 故障%输入框 |
| **故障隔离** | 业务故障熔断，下单、营销业务依旧正常工作 | 三个舱状态互不干扰 |

### ⚠ 重要区分：限流拒绝 ≠ 业务报错 ≠ 降级

| 类型 | 说明 |
|------|------|
| **限流拒绝** | 并发已满，请求被挡在舱入口，业务逻辑完全没有执行，**不计入**熔断器失败统计 |
| **业务报错** | 请求成功进入舱并执行业务，代码抛出错误，**参与**熔断器失败率计算 |
| **降级** | 熔断器 Open，执行 fallback 兜底函数，**完全不执行**真实业务，返回成功兜底结果 |

## 熔断器状态流转

```
Closed (正常) ──[错误占比超阈值]──▶ Open (熔断阻断)
    ▲                                         │
    │                                         ▼
    └────[试探成功]◀──── HalfOpen (试探恢复) ◀──[冷却时间到期]
                              │
                              ├──▶ 试探成功 ──▶ Closed (恢复)
                              └──▶ 试探失败 ──▶ Open (继续熔断)
```

| 状态 | 颜色 | 说明 |
|------|------|------|
| **Closed** | 🟢 绿色 | 正常接收业务请求，统计窗口内持续统计成功/失败；失败占比达阈值切换到 Open |
| **Open** | 🔴 红色 | 直接拒绝真实下游调用；营销舱命中降级兜底逻辑返回缓存数据；其它舱直接返回熔断拒绝错误 |
| **HalfOpen** | 🟡 黄色 | 等待冷却窗口期到期后自动进入，放行少量试探流量去访问真实下游服务 |

## 功能特性

- **信号量并发限流** — 控制单个业务最大并发请求，超过上限直接快速拒绝，不堆积协程
- **熔断器故障熔断** — 统计业务请求的成功、失败，失败占比达到阈值触发熔断，拒绝新请求
- **熔断冷却 + 半开试探恢复** — 熔断经过冷却时间进入半开状态，放行请求探测业务是否恢复
- **业务降级 Fallback** — 营销舱支持降级，熔断器 Open 时执行兜底函数返回缓存数据
- **网页故障注入** — 营销舱、报表辅助舱支持网页端配置故障开关、故障百分比，无需修改代码
- **Web 可视化界面** — 实时查看舱状态、各项统计指标；网页直接修改参数；事件日志实时输出
- **一键场景演示** — 内置 3 个预设场景，一键完成参数配置，适合课堂投屏演示
- **日志过滤** — 支持全部日志 / 仅熔断器事件 / 仅降级事件三种过滤模式

## 内置 3 个业务舱

| 舱名 | 演示功能 | 降级 | 故障注入 |
|------|---------|------|---------|
| **下单核心舱** | 限流功能 | ❌ 无 | ❌ 无 |
| **营销舱** | 降级 Fallback | ✅ 支持 | ✅ 支持 |
| **报表辅助舱** | 熔断功能 | ❌ 无 | ✅ 支持 |

## 系统架构

```
浏览器网页前端
    ↓ HTTP接口
Go后端服务
    ├── 3个 BusinessCabin 水密业务舱（互相完全隔离）
    │   ├── 下单核心舱（无降级、无故障注入）
    │   ├── 营销舱（支持 fallback降级 + 网页故障注入）
    │   └── 报表辅助舱（无降级 + 网页故障注入）
    ├── CircuitBreaker 熔断器：Closed / Open / HalfOpen 三状态机
    ├── semaphore 信号量：每个舱独立控制最大并发
    ├── SimpleErrGroup：协程组，批量发起模拟请求
    ├── 全局 faultConfig 故障配置：内存存储，重启丢失
    └── Metrics 指标：每个舱独立统计（总任务、成功、限流拒绝、熔断拒绝、业务报错、降级次数）
```

## 快速开始

### 环境要求

- Go 1.21+
- 现代浏览器（推荐 Chrome / Edge）

### 运行项目

```bash
# 1. 初始化 go 模块
go mod init go-watertight-cabin-demo

# 2. 配置国内代理（可选，解决依赖拉取问题）
go env -w GOPROXY=https://goproxy.cn,direct

# 3. 下载依赖
go mod tidy

# 4. 运行项目
go run .
```

浏览器访问：**http://127.0.0.1:8080**（建议无痕窗口，避免浏览器缓存干扰页面渲染）

### 编译可执行文件

```bash
go build -o go-watertight-cabin-demo .
```

## 网页界面说明

### 参数输入框（每个业务舱独立配置）

| 参数 | 说明 |
|------|------|
| **最大并发** | 该业务舱允许同时处理的请求上限，超过直接限流拒绝 |
| **失败触发熔断%** | 统计样本内，失败请求占比达到该百分比就触发熔断 |
| **统计样本请求数** | 需要收集多少条请求作为判断样本；样本数量不足不会触发熔断 |
| **熔断冷却时间(s)** | 熔断打开之后，等待多少秒，才进入半开试探阶段 |

### 故障注入面板（营销舱、报表辅助舱可见）

- **模拟业务故障勾选框** — 故障总开关，勾选才会启用
- **故障%** — 0-100，100 代表每次请求必模拟业务报错
- **【设置故障】按钮** — 修改完成必须点击按钮，配置才提交后端生效

### 舱卡片状态背景色

舱卡片整体底色跟随熔断器状态同步变化（800ms 轮询自动更新）：

| 状态 | 卡片底色 |
|------|---------|
| 🟢 Closed正常 | 浅绿色 |
| 🟡 HalfOpen试探恢复 | 浅黄色 |
| 🔴 Open熔断阻断 | 浅红色 |

> 投屏演示时，无需细读文字，通过卡片底色即可一眼识别哪个舱发生熔断。

### 页面按钮

| 按钮 | 功能 |
|------|------|
| ① 发起第一轮批量请求 | 发送批量模拟请求，用于制造故障场景 |
| ② 等待熔断恢复窗口期 | sleep 等待，观察熔断器是否切换半开状态 |
| ③ 发起第二轮试探请求 | 半开状态下发送请求，探测业务是否恢复 |
| ④ 重置所有舱状态 | 指标清零、日志清空，全部舱恢复绿色初始状态 |
| 【清空日志】 | 只清空日志面板，保留舱指标、熔断器状态不变 |
| 【应用配置】 | 蓝色按钮，修改舱参数后点击生效 |
| 【设置故障】 | 红色按钮，修改故障注入参数后点击生效 |

### 日志面板

- **清空日志** — 仅清空网页日志面板内容，不修改舱指标、熔断器状态
- **日志过滤下拉选择器** — 全部日志 / 仅熔断器事件 / 仅降级事件

## API 接口

| 接口 | 方法 | 作用 |
|------|------|------|
| `/api/status` | GET | 获取全部舱状态、指标、事件日志、故障配置，前端 800ms 定时拉取刷新页面 |
| `/api/setFault` | POST | 设置故障注入：舱名称、故障开关 enable、故障百分比 faultPercent |
| `/api/runFirst` | POST | 发起第一轮批量模拟请求 |
| `/api/waitHalfOpen` | POST | 等待熔断恢复窗口期 |
| `/api/runSecond` | POST | 发起第二轮试探请求 |
| `/api/reset` | POST | 重置全部舱，指标清零、日志清空，恢复初始状态 |
| `/api/applyConfig` | POST | 接收网页参数，重建业务舱，动态更新配置 |

## 实验操作指南

### 实验一：演示并发限流

**目标：** 观察并发超限出现限流拒绝，熔断器保持绿色，不会触发熔断。

**操作步骤：**

1. 点击紫色按钮【场景 A - 限流压力测试】，程序自动完成重置，设置核心舱最大并发 = 2
2. 点击 ① 发起第一轮批量请求

**观察现象：**

- 状态依旧 🟢 绿色正常
- 限流拒绝计数上涨，成功等于设置的最大并发
- **原理：** 并发已满直接拒绝，业务没有执行，不会产生业务报错，熔断器不会触发熔断

### 实验二：完整演示熔断器生命周期（重点）

**使用报表辅助舱，开启故障注入，故障% = 100，模拟下游完全故障。**

**操作步骤：**

1. 点击紫色按钮【场景 C - 报表舱故障隔离】，自动重置，报表舱故障 100% 开启
2. 点击 ① 发起第一轮批量请求 → 业务报错上涨，状态切换 🔴 红色 Open 熔断阻断
3. 点击 ② 等待熔断恢复窗口期 → 状态变为 🟡 黄色 HalfOpen 半开试探
4. 点击 ③ 发起第二轮试探请求：
   - **分支 A（故障保持开启）：** 试探请求报错 → 立刻切回 🔴 红色熔断
   - **分支 B（关闭故障）：** 取消模拟业务故障 → 试探全部成功 → 切回 🟢 绿色正常

> ✨ **核心演示现象：** 报表舱故障熔断，下单舱、营销舱完全不受影响，实现故障隔离。

### 实验三：演示营销舱熔断 + 降级 Fallback

**前提：营销舱熔断冷却时间设置为 30 秒。**

**操作步骤：**

1. 点击紫色按钮【场景 B - 营销舱熔断 + 降级演示】
2. 反复点击 ① 发起第一轮批量请求，直到营销舱状态变为 🔴 红色 Open
3. ⚠️ **必须在 30 秒冷却窗口期以内，立刻再次点击 ① 发起第一轮批量请求**

**预期现象：**

- 控制台输出：`[营销舱-降级兜底] 返回缓存活动数据`
- 网页营销舱面板：降级次数数字上涨，熔断拒绝保持 0
- 不会执行真实业务函数

> ⚠ **坑：** 如果等待超过 30 秒再点击，Allow() 内部自动切换 HalfOpen 放行，降级不会触发。

## 调参实验参考

| 参数调整 | 效果 |
|---------|------|
| 调高失败触发熔断% = 80 | 需要 80% 请求失败才熔断；同样大量报错，失败率只有 66%，不会触发红色熔断 |
| 调高统计样本请求数 = 100 | 需要攒够 100 条请求样本；只发送 25 条请求，样本不足，不会熔断 |
| 调高熔断冷却时间(s) = 30 | 熔断变红后，需要等待 30 秒才进入半开状态；降级演示必须调大这个参数 |
| 调大最大并发 = 20 | 限流拒绝变少，更多请求可以执行业务，更容易积累报错触发熔断 |

### 故障注入调参

| 配置 | 效果 |
|------|------|
| enable = true, faultPercent = 100 | 每次必报错，快速打熔断 |
| enable = true, faultPercent = 50 | 一半成功一半失败，可以观察熔断器震荡 |
| enable = true, faultPercent = 0 | 开关打开但是业务全部成功，模拟下游故障恢复 |

> **关键理解：** 熔断触发需要两个条件同时满足：① 收集足够统计样本；② 失败占比达到阈值。

## 优缺点与适用场景

### 优点

- **故障隔离，阻止雪崩（核心价值）** — 单个业务故障，只会消耗本舱的并发配额，不会抢占其他业务资源
- **熔断配合降级，保留部分业务可用** — 非核心业务故障熔断，执行 fallback 返回兜底缓存数据
- **快速失败，避免请求堆积** — 信号量满直接拒绝；熔断打开优先执行降级/快速返回错误
- **每个舱独立配置策略** — 核心业务、非核心业务可以设置不同的并发、熔断阈值、降级回调
- **可观测** — 每个舱独立统计指标（含降级次数），便于定位故障点
- **可视化故障注入** — 网页界面即可模拟下游多种故障工况，教学演示非常方便

### 缺点与注意事项

- **资源碎片化** — 舱划分越多，资源越碎片化；空闲舱的并发配额不能借给其他舱使用
- **参数调优难度高** — 参数设置错误会出现误限流、频繁熔断器震荡
- **仅进程内防护** — 无法防护 CPU 打满、OOM、机器宕机，不能替代 K8s 容器资源限制
- **需要区分错误类型** — 用户参数错误、鉴权失败不应计入熔断统计，否则会误触发熔断
- **Demo 半开逻辑简化** — 生产熔断器半开只放行少量试探请求
- **回调函数容易丢失** — 重建业务舱对象时，必须手动复制 fallback 回调函数
- **增加代码复杂度** — 小简单系统会造成过度设计
- **故障注入配置内存存储** — 进程重启全部丢失，仅教学演示，不可上生产

### 适合场景

- 微服务，调用多个外部下游 RPC、DB、第三方 HTTP 接口
- 系统区分核心业务、非核心业务，希望非核心故障不影响核心链路
- 存在报表、导出等重风险慢业务
- 需要防止慢调用耗尽 goroutine、数据库连接池

### 不建议使用场景

- 简单单体小项目，外部依赖很少，属于过度设计
- 故障根源是 CPU/OOM 进程整体资源耗尽
- 以消息队列异步消费为主的系统

## 生产环境注意事项

> ⚠ **重要：本项目是教学 Demo，禁止直接复制上线生产环境。**

### 防护组合拳

完整的弹性防护顺序：**超时设置 > 舱壁隔离（信号量限流） > 熔断器 > 降级兜底返回数据**，多层防护缺一不可。

### 关键差异

| 维度 | Demo 实现 | 生产环境建议 |
|------|----------|------------|
| 信号量限流 | TryAcquire 非阻塞快速拒绝 | 根据业务选择非阻塞或阻塞等待 |
| 熔断器统计 | 简单计数窗口 | 使用滑动窗口（Sentinel / Resilience4j） |
| 半开试探 | 放行全部流量 | 只允许极少量试探请求 |
| 错误分类 | 所有 error 都统计为失败 | 区分业务逻辑错误与依赖故障错误 |
| 指标存储 | 内存存储，重启丢失 | 上报 Prometheus，配置告警 |
| 故障注入 | 网页端内存配置 | 使用 Chaos-Mesh 等专业混沌工程平台 |

- 前端不再无条件执行 innerHTML 全量销毁重建 DOM；仅舱卡片数量变化才全量重建 DOM

- 使用 `document.activeElement` 焦点判断，光标在输入框/复选框编辑时，不会被轮询刷掉用户输入

> 局限：输入框失去焦点但未点击按钮提交，下一轮轮询会被后端旧配置回填。演示场景建议修改参数后立刻点击按钮提交。
