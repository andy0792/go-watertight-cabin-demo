# go-watertight-cabin-demo

> **Go 实现的网页可视化教学 Demo，演示水密隔舱模式（Bulkhead）+ 信号量并发限流 + 熔断器 CircuitBreaker + 业务降级 Fallback + 网页故障注入。**
>
> 非开发人员仅靠点击按钮、修改网页数字就可以理解分布式故障隔离原理。

---

## 项目概述

**类比轮船水密隔舱：** 单个舱故障进水，不会造成整艘船沉没；业务模块故障，不会把整个应用拖垮，实现故障隔离。

### 分布式保护三板斧：限流、熔断、降级

| 机制 | 一句话区分 | 作用对象 | 核心目的 |
|------|-----------|---------|---------|
| **限流** | 防流量太大，管入口 | 挡突发流量，保护自己不被打垮 | 控制并发/请求量，超出阈值直接拒绝 |
| **熔断** | 防雪崩，管下游 | 下游大量报错就切断调用 | 防止故障链式扩散 |
| **降级** | 防自己扛不住，管自身 | 舍弃非核心逻辑，返回兜底结果 | 保障核心业务可用 |

**三者配合分工：** 限流挡流量，熔断断坏依赖，降级保核心业务。本 Demo 完整实现限流、熔断、熔断触发后的 fallback 业务降级兜底，同时支持网页端可视化故障注入，不用改代码即可模拟下游各种故障工况。

> 💡 **容易混淆点：** 熔断是手段，降级往往是熔断触发之后执行的兜底行为。熔断器打开之后，一般就执行降级逻辑返回兜底结果。
>
> 💡 **记忆口诀：** 限流挡流量，熔断断下游，降级保自己。

## 熔断器状态流转

```
Closed (正常) ──[错误占比超阈值]──▶ Open (熔断阻断)
    ▲                                         │
    │                                         ▼
    └────[试探成功]◀──── HalfOpen (试探恢复) ◀──[冷却时间到期]
                              │
                              ├──▶ 试探成功 ──▶ Closed (恢复)
                              └──▶ 试探失败 ──▶ Open (继续熔断)
```

| 状态 | 颜色 | 说明 |
|------|------|------|
| **Closed** | 🟢 绿色 | 正常接收业务请求，统计窗口内持续统计成功/失败；失败占比达阈值切换到 Open |
| **Open** | 🔴 红色 | 直接拒绝真实下游调用；营销舱命中降级兜底逻辑返回缓存数据；其它舱直接返回熔断拒绝错误 |
| **HalfOpen** | 🟡 黄色 | 等待冷却窗口期到期后自动进入，放行少量试探流量去访问真实下游服务 |

## 1. 项目功能简介

每个业务拥有独立隔离舱，舱与舱之间完全隔离互不影响，提供保护机制：

- **信号量并发限流：** 控制单个业务最大并发请求，超过上限直接快速拒绝，不堆积协程。
- **熔断器故障熔断：** 统计业务请求的成功、失败，失败占比达到阈值触发熔断，拒绝新请求，防止故障雪崩。
- **熔断冷却 + 半开试探恢复：** 熔断经过冷却时间，进入半开状态，放行请求探测业务是否已经恢复；试探成功恢复正常；试探失败立刻再次熔断。
- **业务降级 Fallback：** 营销舱支持降级，熔断器 Open 时执行兜底函数返回缓存数据，不再调用真实业务；下单、报表舱无降级。
- **网页故障注入：** 营销舱、辅助舱-报表支持网页端配置故障开关、故障百分比；无需修改代码、无需重新编译，模拟下游正常、不稳定、完全故障。核心舱-下单不支持故障注入，始终业务正常。
- **Web 可视化界面：** 实时查看舱状态、各项统计指标；网页直接修改参数；事件日志实时输出。

### 内置 3 个业务舱，分工设定

| 舱名 | 演示功能 | 降级 | 故障注入 |
|------|---------|------|---------|
| **核心舱-下单** | 限流功能 | ❌ 无 | ❌ 无 |
| **营销舱** | 降级 Fallback | ✅ 支持 | ✅ 支持 |
| **辅助舱-报表** | 熔断功能 | ❌ 无 | ✅ 支持 |

## 2. 核心概念通俗讲解

| 概念 | 通俗比喻 | 网页 UI 标识 |
|------|---------|-------------|
| **水密隔舱 (Bulkhead)** | 轮船独立隔间，一个隔间故障，其他隔间不受影响 | 3 张独立业务卡片面板 |
| **并发限流（信号量）** | 窗口最多同时接待 N 个人，人多直接告知繁忙 | 参数：最大并发 |
| **熔断器 Closed** | 业务健康，全部请求放行 | 🟢 Closed 正常（允许访问） |
| **熔断器 Open** | 业务故障，拒绝新来请求，阻止故障扩散 | 🔴 Open 熔断阻断（拒绝访问） |
| **熔断器 HalfOpen** | 冷却结束，放少量请求试探业务是否修复 | 🟡 HalfOpen 试探恢复（小流量测试） |
| **降级 Fallback** | 熔断打开，不走真实业务，返回缓存兜底数据 | 指标：降级次数 |
| **故障注入** | 模拟下游故障概率，0-100% 可调 | 每个舱面板：勾选框 + 故障%输入框 |
| **故障隔离** | 业务故障熔断，下单、营销业务依旧正常工作 | 三个舱状态互不干扰 |

### ⚠ 重要区分：限流拒绝 ≠ 业务报错 ≠ 降级

| 类型 | 说明 |
|------|------|
| **限流拒绝** | 并发已满，请求被挡在舱入口，业务逻辑完全没有执行，**不计入**熔断器失败统计 |
| **业务报错** | 请求成功进入舱并执行业务，代码抛出错误，**参与**熔断器失败率计算 |
| **降级** | 熔断器 Open，执行 fallback 兜底函数，**完全不执行**真实业务，返回成功兜底结果 |

## 3. 系统整体架构

```
浏览器网页前端
    ↓ HTTP接口
Go后端服务
    ├── 3个 BusinessCabin 水密业务舱（互相完全隔离）
    │   ├── 核心舱-下单（无降级、无故障注入）
    │   ├── 营销舱（支持 fallback降级 + 网页故障注入）
    │   └── 辅助舱-报表（无降级 + 网页故障注入）
    ├── CircuitBreaker 熔断器：Closed / Open / HalfOpen 三状态机
    ├── semaphore 信号量：每个舱独立控制最大并发
    ├── SimpleErrGroup：协程组，批量发起模拟请求
    ├── 全局 faultConfig 故障配置：内存存储，重启丢失
    └── Metrics 指标：每个舱独立统计（总任务、成功、限流拒绝、熔断拒绝、业务报错、降级次数）
```

### 网页前端与后端接口

| 接口 | 作用 |
|------|------|
| `GET /api/status` | 获取全部舱状态、指标、事件日志、故障配置，前端 800ms 定时拉取刷新页面 |
| `POST /api/setFault` | 设置故障注入：舱名称、故障开关 enable、故障百分比 faultPercent |
| `POST /api/runFirst` | 发起第一轮批量模拟请求 |
| `POST /api/waitHalfOpen` | 等待熔断恢复窗口期 |
| `POST /api/runSecond` | 发起第二轮试探请求 |
| `POST /api/reset` | 重置全部舱，指标清零、日志清空，恢复初始状态 |
| `POST /api/applyConfig` | 接收网页参数，重建业务舱，动态更新配置 |

### 前端渲染优化说明

- 前端不再无条件执行 innerHTML 全量销毁重建 DOM；仅舱卡片数量变化才全量重建 DOM
- 平时只局部更新指标、熔断器状态文本
- 使用 `document.activeElement` 焦点判断，光标在输入框/复选框编辑时，不会被轮询刷掉用户输入

> 局限：输入框失去焦点但未点击按钮提交，下一轮轮询会被后端旧配置回填。演示场景建议修改参数后立刻点击按钮提交。

## 4. 编译与运行命令说明

> 🎯 **非开发人员优先阅读本节：拿到源码第一步，先把项目跑起来，先看效果再研究代码。**

### 场景：把整套 Go 源码复制到全新文件夹（示例路径：D:\\go-cabin）

#### Windows CMD 完整操作

```bash
# 进入新的工程目录
cd /d D:\go-cabin

# 1. 初始化go模块，模块名可以自定义

# 2. 自动扫描代码，下载补齐全部第三方依赖，生成go.mod、go.sum

go run go-go.go

go build .
```

## 5. 网页界面说明

### 页面说明文字

> 每个业务独立隔离舱，通过信号量限制最大并发请求；请求失败占比超标自动触发熔断器。
>
> - 🟢 **Closed 正常（允许访问）**：正常放行请求
> - 🟡 **HalfOpen 试探恢复（小流量测试）**：放行少量请求探测下游是否恢复
> - 🔴 **Open 熔断阻断（拒绝访问）**：直接拒绝新的业务请求
>
> 📌 **营销舱降级演示避坑要点：**
> - 营销舱熔断冷却时间改成 30 秒
> - 开启模拟业务故障，故障% = 100，点设置故障
> - 请求打到红色 Open 熔断后，**禁止点重置**，再次发请求，观察降级次数上涨
>
> 备注：营销舱支持故障注入 + 降级兜底；报表舱支持故障注入，无降级；核心舱-下单无故障注入开关。

### 参数输入框（每个业务舱独立配置）

| 参数 | 说明 |
|------|------|
| **最大并发** | 该业务舱允许同时处理的请求上限，超过直接限流拒绝 |
| **失败触发熔断%** | 统计样本内，失败请求占比达到该百分比就触发熔断 |
| **统计样本请求数** | 需要收集多少条请求作为判断样本；样本数量不足不会触发熔断 |
| **熔断冷却时间(s)** | 熔断打开之后，等待多少秒，才进入半开试探阶段 |

> 🎯 **降级演示小技巧：** 做 PPT 演示营销舱降级，把营销舱熔断冷却时间设置为 30s；打到 Open 红色之后，30 秒之内立刻发起新一轮请求，才能命中降级。如果等待超过冷却时间，Allow 自动切 HalfOpen 放行，降级不会触发。

### 故障注入面板（营销舱、辅助舱-报表可见）

- **模拟业务故障勾选框：** 故障总开关，勾选才会启用
- **故障%：** 0-100，100 代表每次请求必模拟业务报错
- **【设置故障】按钮：** 修改完成必须点击按钮，配置才提交后端生效

### 舱状态展示

| 状态 | 说明 |
|------|------|
| 🟢 **Closed 正常（允许访问）** | 正常状态，全部请求放行 |
| 🟡 **HalfOpen 试探恢复（小流量测试）** | 半开，放行请求探测业务是否恢复 |
| 🔴 **Open 熔断阻断（拒绝访问）** | 熔断生效，直接拒绝新请求 |

### 统计指标

| 指标 | 说明 |
|------|------|
| **总任务** | 进入本舱的全部请求数量 |
| **成功** | 业务逻辑正常返回成功 |
| **限流拒绝** | 并发已满，被信号量拦截（业务未执行） |
| **熔断拒绝** | 熔断器打开，无降级时拒绝请求 |
| **业务报错** | 请求已经进入舱执行业务，业务抛出异常 |
| **降级次数** | 熔断器 Open，执行 fallback 兜底的请求计数 |

### 页面按钮

| 按钮 | 功能 |
|------|------|
| ① 发起第一轮批量请求 | 发送批量模拟请求，用于制造故障场景 |
| ② 等待熔断恢复窗口期 | sleep 等待，观察熔断器是否切换半开状态 |
| ③ 发起第二轮试探请求 | 半开状态下发送请求，探测业务是否恢复 |
| ④ 重置所有舱状态 | 指标清零、日志清空，全部舱恢复绿色初始状态 |

> 修改舱参数之后，点击蓝色【应用配置】新参数才会生效；注意重建营销舱时代码要复制 fallback 降级回调。
>
> 修改故障注入参数，点击红色【设置故障】提交后端生效。

## 6. 完整演示实验操作指南

> 🎯 **非开发人员优先做本节，跑 3 个实验，直观看懂限流、熔断、降级现象。**

### 🧪 实验一：演示【并发限流】

**目标：** 观察并发超限出现限流拒绝，熔断器保持绿色，不会触发熔断。

1. 点击【④ 重置所有舱状态】清零
2. 修改【核心舱-下单】参数：
   - 最大并发：5
   - 失败触发熔断%：50
   - 统计样本请求数：40
   - 熔断冷却时间(s)：1
   - 点击【应用配置】
3. 点击 ① 发起第一轮批量请求，会一次性发起 10 个下单请求

**观察现象：**

- 状态依旧 🟢 绿色正常
- 限流拒绝计数上涨，成功等于最大并发 5
- **原理：** 并发已满直接拒绝，业务没有执行，不会产生业务报错，熔断器不会触发熔断

### 🧪 实验二：完整演示熔断器生命周期（重点）

**使用【辅助舱-报表】，开启故障注入，故障% = 100，模拟下游完全故障。**

1. 点击【④ 重置所有舱状态】回到干净初始状态
2. 报表舱：勾选模拟业务故障，故障% = 100，点击【设置故障】
3. 参数参考：最大并发 8，失败触发熔断%：40，统计样本请求数：30，熔断冷却时间(s)：1，【应用配置】
4. 点击 ① 发起第一轮批量请求

**现象：** 业务报错持续上涨；样本收集完成，失败占比超过阈值，状态切换 🔴 红色 Open 熔断阻断

5. 点击 ② 等待熔断恢复窗口期，冷却时间结束，状态变为 🟡 黄色 HalfOpen 半开试探
6. 点击 ③ 发起第二轮试探请求：
   - **分支 A（故障保持开启）：** 试探请求出现报错 → 立刻切回 🔴 红色熔断
   - **分支 B（关闭故障）：** 试探全部成功 → 切回 🟢 绿色正常，熔断解除

**实验结束，点击【④ 重置所有舱状态】。**

> ✨ **核心演示现象：** 报表舱故障熔断，下单舱、营销舱完全不受影响，实现故障隔离（水密隔舱核心思想）。

### 🧪 实验三：演示【营销舱熔断+降级 Fallback】

**前提：营销舱熔断冷却时间设置为 30 秒（PPT 演示拉长窗口期，避免 Allow 自动切 HalfOpen）。**

1. 点击【④ 重置所有舱状态】清零
2. 修改营销舱参数：熔断冷却时间(s) = 30，点击【应用配置】
3. 营销舱：勾选模拟业务故障，故障% = 100，点击【设置故障】
4. 反复点击 ① 发起第一轮批量请求，直到营销舱状态变为 🔴 红色 Open 熔断阻断
5. ⚠️ **必须在 30 秒冷却窗口期以内，立刻再次点击【① 发起第一轮批量请求】**

**预期现象：**

- 控制台输出：`[营销舱-降级兜底] 返回缓存活动数据`
- 网页营销舱面板：降级次数数字上涨，熔断拒绝 (CbReject) 保持 0
- 不会执行真实 bizMarketing 业务函数，不会打印业务 SUCCESS/DB 超时报错

> ⚠ **坑：** 如果等待超过 30 秒再点击，Allow() 内部自动切换 HalfOpen 放行，降级不会触发。

## 7. 调参实验参考

修改参数，点击应用配置，再跑完整流程，观察现象。

| 参数调整 | 效果 |
|---------|------|
| 调高失败触发熔断% = 80 | 需要 80% 请求失败才熔断；同样大量报错，失败率只有 66%，不会触发红色熔断 |
| 调高统计样本请求数 = 100 | 需要攒够 100 条请求样本；只发送 25 条请求，样本不足，无论报错多少，不会熔断 |
| 调高熔断冷却时间(s) = 30 | 熔断变红后，需要等待 30 秒才进入半开状态；降级演示必须调大这个参数 |
| 调大最大并发 = 20 | 限流拒绝变少，更多请求可以执行业务，更容易积累报错触发熔断 |

### 故障注入调参

| 配置 | 效果 |
|------|------|
| enable = true, faultPercent = 100 | 每次必报错，快速打熔断 |
| enable = true, faultPercent = 50 | 一半成功一半失败，可以观察熔断器震荡 |
| enable = true, faultPercent = 0 | 开关打开但是业务全部成功，模拟下游故障恢复 |

> **关键理解：** 熔断触发需要两个条件同时满足：① 收集足够统计样本；② 失败占比达到阈值。

## 8. 优缺点与适用/不适用场景

### ✅ 优点

- **故障隔离，阻止雪崩（核心价值）：** 单个业务故障，只会消耗本舱的并发配额，不会抢占其他业务资源；局部故障不会演变为整个服务雪崩。
- **熔断配合降级，保留部分业务可用：** 非核心业务故障熔断，执行 fallback 返回兜底缓存数据，保障接口不直接报错。
- **快速失败，避免请求堆积：** 信号量满直接拒绝；熔断打开优先执行降级/快速返回错误，减少无效等待、goroutine 堆积。
- **每个舱独立配置策略：** 核心业务、非核心业务可以设置不同的并发、熔断阈值、降级回调。
- **可观测：** 每个舱独立统计指标（含降级次数），便于定位故障点。
- **可视化故障注入：** 网页界面即可模拟下游多种故障工况，不需要修改源码、重新编译，教学演示非常方便。

### ⚠ 缺点与坑

- **资源碎片化：** 舱划分越多，资源越碎片化；空闲舱的并发配额，不能借给流量突增的其他舱使用，资源利用率下降。
- **参数调优难度高：** 参数设置错误会出现误限流、频繁熔断器震荡（Open ↔ HalfOpen 来回跳动），需要压测结合业务 P99 延迟调参。
- **仅进程内防护：** 只能防护下游慢调用耗尽本进程 goroutine、连接；无法防护 CPU 打满、OOM、机器宕机，不能替代 K8s 容器资源限制。
- **需要区分错误类型：** Demo 把所有 error 都统计为失败；生产中用户参数错误、鉴权失败属于业务逻辑错误，不应该计入熔断统计，否则会误触发熔断。
- **Demo 半开逻辑简化：** 生产熔断器半开只放行少量试探请求；本 Demo 半开放行全部请求，如果下游刚恢复，大量流量会直接再次打垮下游。
- **回调函数容易丢失：** 重建 BusinessCabin 结构体，NewCabin 会把 fallback 置 nil，必须手动复制 fallback 回调；单元测试可以复现，网页演示很容易踩这个坑。
- **增加代码复杂度，** 小简单系统会造成过度设计。
- **故障注入配置内存存储：** 进程重启全部丢失，仅教学演示，不可上生产。

### 🎯 适合场景

- 微服务，调用多个外部下游 RPC、DB、第三方 HTTP 接口，下游存在慢、超时风险
- 系统区分核心业务、非核心业务，希望非核心故障不影响核心链路，熔断后执行本地降级兜底
- 存在报表、导出等重风险慢业务
- 需要防止慢调用耗尽 goroutine、数据库连接池，避免服务雪崩

### ❌ 不建议使用场景

- 简单单体小项目，外部依赖很少，属于过度设计
- 故障根源是 CPU/OOM 进程整体资源耗尽，本模式无法解决
- 以消息队列异步消费为主的系统，隔离逻辑更多放在消费者侧

## 9. 课堂演示话术（面向非开发人员，直接照着讲）

### 开场介绍

> "今天演示分布式系统两个重要保护机制：并发限流和熔断器，这个模型叫做水密隔舱，来自轮船设计。轮船划分多个隔间，一个隔间漏水，不会整艘船沉没。对应软件系统，某个业务模块故障，不能把整个系统拖垮。
>
> 我们这里有三个舱：核心舱-下单、营销舱、辅助舱-报表。报表、营销舱可以在网页打开模拟业务故障，模拟下游服务不稳定或者完全挂掉。营销舱额外实现了熔断后的降级兜底。
>
> 界面状态：🟢 绿色正常放行，🟡 黄色小流量试探，🔴 红色熔断拒绝。"

### 演示一：并发限流

> "现在我们把下单舱最大并发设置为 5，同一时间最多处理 5 个请求，一次性发起 10 个请求。
>
> 大家可以看到限流拒绝计数上涨，但是状态依旧是绿色。
>
> 👉 **重点：限流不等于业务报错。** 请求太多，直接挡在门外，业务代码根本没有跑，熔断器不会认为服务故障。限流用来保护自己，防止流量过大把服务压垮。"

### 演示二：熔断器完整生命周期（重点）

> "限流是防止被压垮；熔断器解决下游故障雪崩。
>
> 如果下游大量报错，我们还不停调用它，会出现大量超时，请求堆积，故障扩散到整个系统。熔断器就会断开，停止调用故障服务，给下游留出修复时间。
>
> 我们给报表舱开启模拟故障 100% 报错，大量业务报错，样本收集够，失败比例超过阈值，变成红色熔断阻断。新的请求不再执行业务，直接拒绝。
>
> 熔断不会永远红色，等待冷却时间结束，进入黄色半开试探状态，放少量请求探测服务有没有修好。
>
> 如果试探依旧报错，说明服务还没修好，立刻再次熔断；我们取消模拟故障，下游恢复，试探全部成功，就恢复绿色正常。
>
> 大家注意：报表舱故障熔断，下单、营销舱完全不受影响。这就是水密隔舱故障隔离的价值。"

### 演示三：熔断+降级（营销舱）

> "熔断之后有两种处理策略：直接返回错误，或者执行降级兜底。
>
> 营销舱开启模拟故障打到熔断 Open，熔断器 Open 之后，不再调用真实业务，直接执行本地缓存兜底逻辑，返回可用结果，不对外抛错误。
>
> ⚠️ **演示注意：** 要在熔断冷却窗口期之内发送请求；时间过期熔断器悄悄进入半开，就不会触发降级。"

### 总结

> 1. **限流：** 保护自己，防止并发太大压垮服务；限流拒绝不等于业务失败。
> 2. **熔断器：** 保护不被下游故障雪崩，只统计真正执行业务的成功失败。
> 3. **降级：** 熔断打开之后的兜底策略，返回缓存数据，保障接口可用。
> 4. **熔断器三个状态流转：** 正常 → 熔断阻断 → 半开试探。
> 5. **不是一报错就熔断，** 要收集足够样本，失败占比达到阈值两个条件。
> 6. **半开试探：** 成功就恢复，遇到失败立刻重新熔断。
> 7. **网页故障注入** 可以快速模拟下游各种故障，不用修改代码。
>
> 注意这个是演示 Demo，生产环境会更加复杂。"

## 10. 生产环境注意事项与坑点

> ⚠ **重要：本项目是教学 Demo，禁止直接复制上线生产环境。**

### 信号量限流

- Demo 使用 TryAcquire 非阻塞快速拒绝；生产根据业务选择非阻塞快速失败或者阻塞等待；优先推荐非阻塞防止 goroutine 堆积。

### 熔断器实现差异

- Demo 是简单计数窗口；工业级组件（Sentinel、Resilience4j）使用滑动窗口统计
- Demo 半开放行全部流量；生产半开状态只允许极少量试探请求，防止把刚恢复的下游再次打垮
- 错误分类过滤：用户参数错误、鉴权失败不计入熔断失败统计，只统计下游依赖故障类错误
- Allow() 不是只读查询，具备状态变更副作用；UI 界面状态快照不等于真实运行时状态

### 降级 Fallback 回调

- 重建业务舱对象时，手动复制 fallback 回调函数，防止降级逻辑悄悄丢失
- fallback 内部需要增加超时、panic 保护，防止兜底逻辑本身异常

### 指标与监控告警

- Demo 全部指标内存存储，重启丢失；生产需要上报 Prometheus
- 熔断器状态切换、降级次数突增需要配置告警

### 舱粒度设计

- 最佳实践：按外部依赖划分舱，不要按接口划分舱；一个外部下游对应一个舱，粒度不能过细，也不能过粗

### 防护组合拳

> 完整的弹性防护顺序：**超时设置 > 舱壁隔离（信号量限流） > 熔断器 > 降级兜底返回数据**，多层防护缺一不可。

- 水密隔舱只是止损手段，不会修复下游故障；熔断发生之后，依旧需要人工排查修复故障服务，只是阻止故障扩散。
- 故障注入提醒：Demo 网页故障注入仅用于教学演示；生产环境故障注入请使用 Chaos-Mesh 等专业混沌工程平台，不要自己实现。

## 11. 常见现象答疑

| 问题 | 解答 |
|------|------|
| **限流拒绝数字涨很多，熔断器依旧是绿色？** | 限流拒绝代表请求被拦在入口，业务没有执行，不会算作失败，熔断器不会触发 |
| **已经看到大量业务报错，熔断器不会变红？** | 检查【统计样本请求数】，需要收集足够样本数量，才会计算失败占比；同时确认故障注入开关已经勾选 |
| **半开状态一发起第二轮请求，立刻再次熔断？** | 辅助舱-报表故障注入仍然开启，请求会报错；半开试探遇到报错，规则就是立刻切回熔断 |
| **网页 UI 显示 Open 熔断阻断，但是新请求没有触发降级？** | 高频坑！cb.Allow() 有状态变更副作用；熔断冷却时间到期，调用 Allow 会自动切换 HalfOpen 放行请求；UI 只是快照，不等于真实运行状态。做演示调大熔断冷却时间，在窗口期之内发送请求 |
| **单元测试降级用例 PASS，网页演示降级不生效？** | 重建 BusinessCabin 结构体，忘记复制 fallback 回调函数，fallback 被置 nil；单元测试自己 NewCabin 并手动赋值 fallback，不受影响；网页点击应用配置重建舱触发 bug |
| **输入框修改数字，光标移开还没有点按钮，数值跳回旧值？** | 前端采用 document.activeElement 焦点保护方案；仅光标在输入框内编辑时保护输入；失去焦点后轮询会回填后端真实配置；操作习惯：修改参数后立刻点击提交按钮 |
| **长时间反复跑演示，内存占用越来越高？** | Demo 没有做内存优化，测试完成建议点击重置或者重启程序释放内存 |

### 单元测试、接口测试、集成测试三者概念科普

1. 单元测试要求每次运行结果完全稳定可复现；因此不要直接调用带有随机故障模拟的业务函数 bizMarketing/bizReport，直接使用 cabin.Run() 传入确定回调

3. 每一个测试 case 开头，必须调用重置：`cabinOrder.Reset()`, `cabinMarketing.Reset()`, `cabinReport.Reset()`, `resetFaultConfig()`
4. 集成测试内部会执行 sleep 等待熔断冷却时间，整套测试耗时会变长，属于预期现象

## 13. 迭代：故障注入功能（已完成）

### 迭代效果

为营销舱、报表舱增加故障模拟配置；下单舱作为核心业务，不支持故障模拟，始终业务正常。

每个舱包含两组配置：

| 配置项 | 说明 |
|--------|------|
| **Enable 故障总开关** | 关闭则完全不模拟故障，业务 100% 成功；打开之后故障百分比才生效 |
| **FaultPercent 故障百分比（0-100）** | 0%：开关打开也全部业务成功；50%：50% 概率返回业务异常；100%：每次请求必返回故障 |

后端新增接口：`POST /api/setFault`，接收舱名称、开关状态、故障百分比。`/api/status` 接口同步返回各舱故障配置，网页 UI 回显。

### 典型演示配置

| 场景 | 配置 |
|------|------|
| 快速触发熔断 | enable=true, faultPercent=100 |
| 模拟下游半不稳定 | enable=true, faultPercent=50 |
| 模拟故障恢复 | enable=true, faultPercent=0 |

### 迭代收益

## 15. 关键代码说明

> 🎯 **建议：先跑通上面实验，看懂网页现象之后，再来阅读本章节源码分析。**

### 15.1 熔断器状态枚举

```go
type State int32

const (
    StateClosed   State = 0 // 正常放行
    StateOpen     State = 1 // 熔断打开
    StateHalfOpen State = 2 // 半开试探
)

func (s State) String() string {
    switch s {
    case StateClosed:
        return "Closed"
    case StateOpen:
        return "Open"
    case StateHalfOpen:
        return "HalfOpen"
    default:
        return "Unknown"
    }
}
```

### 15.2 BusinessCabin 水密舱结构体（新增 fallback 降级回调）

每个舱拥有独立信号量、熔断器、统计指标、降级回调函数，实现隔离。

```go
type BusinessCabin struct {
    name           string
    maxConcurrency int64
    sem            *semaphore.Weighted
    cb             *CircuitBreaker
    fallback       func(ctx context.Context) error // 降级兜底函数，nil代表不启用降级
    metrics        CabinMetrics
    mu             sync.Mutex
}
```

### 15.3 业务执行入口 Run（熔断+降级逻辑）

执行顺序：先判断熔断器 → 如果 Open 并且存在 fallback，执行降级兜底 → 再做信号量并发限流 → 执行业务 → 将成功失败结果反馈给熔断器

> ⚠ **重要坑：c.cb.Allow() 不是只读查询函数，具备状态变更副作用！**
>
> Open 状态时间到期，Allow() 内部自动将状态切换为 HalfOpen，返回 true 放行请求。网页 UI 只是状态快照，UI 显示 Open，调用 Allow 之后状态可能已经变化。

```go
func (c *BusinessCabin) Run(ctx context.Context, fn func(ctx context.Context) error) error {
    c.mu.Lock()
    c.metrics.TotalTask += 1
    c.mu.Unlock()

    if !c.cb.Allow() {
        // 熔断器Open，优先执行降级兜底fallback
        if c.fallback != nil {
            c.mu.Lock()
            c.metrics.DegradeCount += 1
            c.mu.Unlock()
            onEventLog(fmt.Sprintf("[%s] 触发降级兜底，返回缓存活动数据", c.name))
            return c.fallback(ctx)
        }
        // 无降级，返回熔断拒绝错误
        c.mu.Lock()
        c.metrics.CbReject += 1
        c.mu.Unlock()
        return errors.New("cabin circuit breaker open: service reject")
    }

    // 信号量非阻塞获取，并发已满直接拒绝
    if !c.sem.TryAcquire(1) {
        c.mu.Lock()
        c.metrics.LimitReject += 1
        c.mu.Unlock()
        return errors.New("cabin semaphore full: concurrency limit reject")
    }
    defer c.sem.Release(1)

    var execErr error
    func() {
        ctxT, cancel := context.WithTimeout(ctx, 3*time.Second)
        defer cancel()
        execErr = fn(ctxT)
    }()

    if execErr != nil {
        c.mu.Lock()
        c.metrics.BusinessError += 1
        c.mu.Unlock()
    } else {
        c.mu.Lock()
        c.metrics.Success += 1
        c.mu.Unlock()
    }
    c.cb.OnResult(execErr != nil)
    return execErr
}
```

> **关键点：** 重建 BusinessCabin 结构体的时候，NewCabin 只会把 fallback 置 nil，必须手动赋值复制旧对象的 fallback 回调函数；单元测试可以稳定复现这个 bug，网页演示容易踩坑。

### 15.4 熔断器状态流转 OnResult

业务执行完成后回调，根据成功失败切换熔断器状态：

- **Closed 状态：** 收集样本，失败占比达到阈值切换为 Open 熔断
- **HalfOpen 半开状态：** 失败立刻切回 Open；成功切回 Closed 恢复正常
- **Open 状态：** 等待冷却时间到期，Allow() 内部自动切换 HalfOpen

### 15.5 故障注入相关结构体与逻辑

```go
type CabinFaultConfig struct {
    Enable       bool `json:"enable"`         // 故障总开关
    FaultPercent int  `json:"fault_percent"`  // 故障百分比 0-100
}

// shouldProduceFault 判断本次请求是否模拟故障
func shouldProduceFault(cabinName string) bool {
    faultMu.Lock()
    defer faultMu.Unlock()
    cfg, ok := faultConfig[cabinName]
    if !ok || !cfg.Enable {
        return false
    }
    p := cfg.FaultPercent
    if p <= 0 {
        return false
    }
    if p >= 100 {
        return true
    }
    return rand.Intn(100) < p
}
```

业务函数 bizMarketing、bizReport 内部调用 shouldProduceFault() 实现动态故障模拟；业务本身逻辑与故障注入解耦。

## 限流 | 熔断 | 降级（精简核心版）

### 一句话区分

| 机制 | 一句话 |
|------|--------|
| **限流** | 防流量太大，管入口，挡住突发流量，保护自己不被打垮 |
| **熔断** | 防雪崩，管下游，下游大量报错就切断调用，不再访问故障依赖 |
| **降级** | 防自己扛不住，管自身，舍弃非核心逻辑，返回兜底结果保核心可用 |

### 1. 限流 RateLimit

- **作用：** 控制并发/QPS，超限直接快速拒绝
- **场景：** 大促、突发流量洪峰
- **常见算法：** 计数器、滑动窗口、漏桶、令牌桶
- **结果：** 返回请求繁忙，不执行业务逻辑

### 2. 熔断 CircuitBreaker

- **状态流转：** Closed(正常) → Open(熔断断开) → HalfOpen(半开试探) → Closed(恢复)
- **场景：** RPC/DB/第三方下游大量报错、超时
- **Closed：** 正常发起调用
- **Open：** 短路，不发起真实请求
- **HalfOpen：** 放少量请求试探下游是否修复

### 3. 降级 Degrade / Fallback

- **例子：** 商品页关掉推荐、返回缓存数据，优先保下单核心链路
- **本 Demo：** 营销舱熔断打开，不走真实业务，直接返回缓存兜底

### 熔断 vs 降级核心区别

| 机制 | 管什么 | 做什么 |
|------|--------|--------|
| **熔断** | 管下游 | 停止调用故障外部依赖 |
| **降级** | 管自己 | 执行兜底逻辑，保障对外返回可用结果 |

### 主流组件

| 组件 | 说明 |
|------|------|
| **Sentinel (阿里)** | 限流、熔断、降级一站式，国内微服务常用 |
| **Resilience4j** | Java 新一代，替代 Hystrix |
| **Hystrix** | 经典老组件，已停止维护 |

### 记忆口诀

> **限流挡流量，熔断断下游，降级保自己。**
